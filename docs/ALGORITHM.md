# 算法假设与 RFC 条款映射

本文件列出实现中所有**非显然的决定**及其规范依据，便于审查。

## 1. 前缀整数（RFC 7541 §5.1）

- 前缀 n∈[1,8]；若前缀值等于 `2^n-1`，读续接字节（低 7 位有效，高位
  表示还有后续）。
- **上界**：规范要求解码器把大于 `2^62-1` 的值当作错误。实现用
  `codec.MaxIntegerValue` 常量，并在每次累加时检查 `add > Max-value`，
  同时用 `shift>=63` 防止移位本身溢出。
- 编码 `AppendInteger(dst, lead, n, v)` 只改写 `lead` 的低 n 位，保留其它位。

## 2. 静态 Huffman（§5.2 + 附录 B）

- 码长表（256 项）是规范性常量；码字不硬编码，而在 `init` 用**规范前缀码**
  算法由码长推导：按 (码长, 符号) 排序，`code = (prev+1) << (len-prevLen)`。
  注意码长按符号并非单调，因此排序是必需的。
- 解码器为二叉前缀树。逐比特下行；遇叶输出符号并回到根。
- **终止/padding 判定**（§5.2）：
  - 流末若正好在根 → 合法（整字节边界结束）。
  - 否则剩余 1..7 个比特只能是 **EOS（30 个 1）的严格前缀**。实现预标记
    从根出发只走 `1` 的路径（`onesSpine`）；剩余深度 >7、落在非叶非 spine
    节点，或 spine 外，都拒绝。
  - 流中出现完整 EOS（符号 256）会走到深度 30 后仍有余位而失败；
    `0xff ff ff ff fc` 等附录向量均拒绝。
- 编码尾部用 EOS 最高位（全 1）填充至字节边界。
- 长度上限在**解码输出**上判定（Huffman 长度与线长不成固定比例）。

## 3. 动态表与字节成本（§2.3.2、§4.1–§4.4）

- 每条目成本 `S = len(name)+len(value)+32`。
- 新条目插到最新端；插入后若 `size > max`，从**最旧端**逐条驱逐直到满足。
- 缩小 `max` 同样触发驱逐；条目顺序不变。
- 若单条成本 `S > max`，插入后它会把**包括自己在内**的所有条目驱逐，
  表为空、size=0；该头部字段**仍然发出**（§4.4 明确允许）。
- 协议索引：1..61 为静态表；62 起为动态表最新端。动态内部下标
  `d = idx-61`，映射 `ents[len(ents)-d]`。

## 4. 表大小更新的位置（§4.2、§6.3）

- 表示 `001xxxxx`（5 位前缀整数）。
- 只允许出现在头块**第一个头部字段表示之前**；一个块开头可有零个或多个
  连续更新，之后出现即 `KindSizeUpdatePosition`。
- 更新值不得超过本方向由 SETTINGS 通告的上限，否则
  `KindSizeUpdateTooLarge`。
- 解码器用 `firstField` 门闩：块开始置真，接受第一个真实字段后置假，
  块结束复位。
- **方向**：对端 SETTINGS 中的 `HEADER_TABLE_SIZE` 约束“我方为编码对端
  内容而维护的表”，即我方**编码器**；不改变我方解码器的接受上限。
  服务端据此把客户端 SETTINGS 应用到 `encoder.UpdateMaxTableSize`。

## 5. 四种表示（§6.1–§6.3）

| 前缀 | 表示 | 是否入表 | 敏感 |
|---|---|---|---|
| `1` (0x80) | 索引 | 引用既有条目 | 否 |
| `01` (0x40, 6 位) | 字面值 + 增量索引 | 是 | 否 |
| `0000` (0x00, 4 位) | 字面值不索引 | 否 | 否 |
| `0001` (0x10, 4 位) | 字面值绝不索引 | 否 | 是 |

- 索引 0 在索引表示中**永远非法**（`KindIndexZero`）；在字面值中 0 表示
  “新名字”，随后必须跟一个字符串。
- 绝不索引表示产出的字段 `Sensitive=true`，且编码端/解码端都**不**把它
  放入动态表。
- 编码器索引选择顺序：动态表精确匹配 → 静态表精确匹配；否则增量索引，
  名字可引用动态/静态表的名字（仅名字）匹配。

## 6. 解压后头部量的三层预算

- `MaxStringLen`：单个 name/value 解压后字节数。
- `MaxHeaderBlockEmitted`：单块所有字段 name+value 之和。
- `MaxHeaderFields`：单块字段条数。

三者独立、先到先拒；超限错误分类为 `KindStringTooLong` /
`KindHeaderListTooLarge`。这限制了“高压缩比炸弹”与字段洪流。

## 7. 失败即毒化、连接隔离

- `DecodeBlock` 任何错误都设置 `poisoned=true`；此后所有调用直接返回
  `KindPoisoned`，不触碰表状态。这建模 RFC 7541“压缩错误是连接错误”：
  一旦失步，后续索引解释全部不可信。
- HTTP/2 服务收到解码错误 → GOAWAY，错误码 `COMPRESSION_ERROR(0x9)`，
  然后关闭 TCP；不会尝试“跳过坏块继续”。
- `Decoder`/`Encoder` 不包含任何共享可变状态；每个连接 `new` 一套。

## 8. 有意不实现/简化

这些是受控本地服务的合理边界，已在代码与测试中显式体现，而非隐藏：

- 不实现 HTTP/2 流级流控的强制执行（WINDOW_UPDATE 被接收但忽略其数值）。
- 不做 HPACK 层之外的完整请求路由；服务固定回 `:status 204`，用途是
  验证编码/解码往返。
- 不做请求体语义；END_STREAM 是应答触发点。
- 伪首部校验（顺序、唯一性）默认提供但可通过 `ValidatePseudo` 开关，
  黄金语料解码不启用（语料只验证 HPACK 本身）。
