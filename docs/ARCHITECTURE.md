# 架构说明

## 1. 分层与依赖方向

```
            ┌───────────────────────────────────────────┐
   HTTP  →  │ api.py (FastAPI: 路由 / 错误码映射 / 模式)    │
            └───────────────────┬───────────────────────┘
                                ▼
            ┌───────────────────────────────────────────┐
            │ service.py (编排：取理论/证据 → 求值 → 记录) │
            └───────┬───────────────┬──────────────┬────┘
                    ▼               ▼              ▼
            ┌──────────────┐ ┌────────────┐ ┌─────────────┐
            │ engine.py    │ │ storage.py │ │ logging.py  │
            │ 推理/解释内核 │ │ SQLite     │ │ JSONL 运行日志│
            └──────┬───────┘ └────────────┘ └─────────────┘
                   ▼
            ┌──────────────┐    ┌────────────────────────┐
            │ grounding.py │    │ language.py (规则语言)  │
            │ grounding/WFS│    └────────────────────────┘
            └──────────────┘
            ┌───────────────────────────────────────────┐
            │ config.py (独立环境配置，零第三方依赖)       │
            └───────────────────────────────────────────┘
```

依赖单向向下：`api → service → {engine, storage, logging}`；
`engine → {grounding, language, errors}`。规则语言层不依赖存储与接口，
因此同一内核既能在 FastAPI 内使用，也能在单元测试与脚本里直接调用。

## 2. 关键设计决定

### 2.1 规则库与证据分离
`storage.py` 只保存**基证据文字**，规则与优先级属于规则层。这样“缺少证据不是反面事实”
可被结构性地保证：存储层只能回答“已知什么”，永远不会因为没有 `P` 而造出 `-P`。

### 2.2 用良基模型而不是搜索 + 启发式
内核把理论编译成一个有限的基（ground）正规逻辑程序，其真原子由
`grounding.well_founded` 的**良基模型**给出：

- 反复施加确定后承算子得到真集合；
- 反复删除最大无根基集得到假集合；
- 直到集合不再变化。

整个过程只做**集合相等**判定，迭代任何字典都不影响不动点，
这就是“规则重排不改变结论”的根本保障（并有全排列与随机洗牌测试守护）。

### 2.3 一个元程序同时承载 supported / provable 两层
`sup:L` 与 `prov:L` 共存于同一程序中。`prov:L` 的默认规则被击败条件引用的是反方规则的
**`sup:` 适用性**——这正是歧义传播（ambiguity propagation）：支持层的争议会阻止上层证明。
若改用反方的 `prov:` 适用性则会退化为“歧义阻断”，会把尼克松菱形这类争议意外裁决掉。

### 2.4 三类论证链的构造与分类
查询时 `engine._build_trees` 枚举所有以证据事实为叶、以目标为根的有限证明树，
用“分支上已出现的结论”切断正推导环，并用 `max_chains` 预算限制组合爆炸（超出即
`resource_exhausted`）。随后 `_classify` 按下述顺序判定每条链：

1. 子前提链被击败 → 本链 `defeat`；
2. 存在 *supported 可适用* 且严格更强的反方链 → `defeat`（指认击败者）；
3. 前提均可证且结论可证 → `support`；
4. 前提悬置 → `pending`；
5. 存在 supported/provable 可适用但**优先级不可比**的反方链 → `pending`（保留冲突）；
6. 与反方相互攻击、双方在良基模型均不成立 → `pending`；
7. 其余有限证据链 → `support`。

强弱比较 `_compare` 返回 `1 / -1 / 0`，`0` 表示**不可比**——绝不猜测优先级。
事实/严格规则恒强于默认规则；两条严格规则冲突在求值期作为 `state_conflict` 拒绝。

### 2.5 四类错误严格分开
`errors.py` 用带稳定 `code` 与 HTTP 状态的异常类表达
`invalid_input / state_conflict / resource_exhausted / computation_failure`。
`service.query` 捕获所有非预期异常并归一为 `computation_failure`，同时写入日志，
避免把内部 bug 误报成输入或资源问题。

## 3. 持久化与并发
- SQLite 开启外键，`cases / evidence / theories` 三表；连接 `check_same_thread=False`，
  每个操作短事务、立即 commit。
- 运行日志为仅追加 JSONL，进程内用锁串行化写；损坏尾行会被读取端跳过。

## 4. 可测试性
- `create_app(settings, store=, logger=)` 显式注入依赖，集成测试用内存 SQLite + 内存日志，
  无需真实端口或文件。
- `tests/unit/oracle.py` 是**算法独立**的预言器（Dung 接地扩展），与内核不共享实现，
  参考答案不由被测核心生成。
